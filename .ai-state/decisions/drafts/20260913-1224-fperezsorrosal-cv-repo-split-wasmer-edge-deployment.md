## Context

The MCP server runs on render.com (`fps-cv.onrender.com/mcp`), a buildpack deploy driven by `runtime.txt`. It works. Two things are missing and one is changing.

Missing: there is nowhere to publish the rendered HTML CV. The HTML renderer produces a self-contained interactive document with theme switching and expandable cards, and it currently goes nowhere — it is reachable only through an MCP tool call. A public CV page is the natural artifact of this project and has no home.

Missing: render.com does not host static sites alongside the service, so publishing the HTML there means a second, unrelated hosting arrangement.

Changing: the MCP spec revision 2026-07-28 removed the `initialize` handshake and `Mcp-Session-Id` entirely — the protocol is now stateless. A horizontally-scaled, session-affinity-free platform stops being a liability and becomes a natural fit.

The maintainer already operates Wasmer and has a live, heavily instrumented Python MCP deployment there (`wasmer-sandbox-mcp.wasmer.app/mcp`) with 41 documented first-party findings covering exactly this path: `anybuild` generating a starlark build file with `python_framework = "mcp"`, cross-installing WASIX wheels from `python-registry.wasix.org`, and deploying via the `wasmer` CLI. That prior art is Tier-1 evidence for this specific question, and it also documents the sharp edges.

The constraints it documents, verified independently on 2026-09-13:

- **`pydantic-core` on the WASIX index tops out at `2.46.4+wasix.2`**, so `pydantic` must be `<2.13.5`. PyPI's current `pydantic` is exactly `2.13.5` — the ceiling is live and binding today, not a future concern.
- **Native C-extension libraries can trap the instance** with no traceback, no log line, just a bare HTTP 500. This project has no such dependency (`jinja2`, `loguru`, `httpx`, `mcp` are pure Python; `pyyaml` and `pydantic-core` have WASIX wheels), but any future one needs a wheel-existence check first.
- **`anybuild` ignores `.gitignore`**, copying the whole project directory into the image except `.venv`, `.git` and `__pycache__`. A large image makes the registry upload fail with a bare HTTP 500.
- **`anybuild` 0.28.x requires `wasmer` CLI ≥ 7.** On 6.1.0 it shells out to a rejected `--volume` flag and its package upload fails with a bare 500.
- **`anybuild`'s MCP provider injects `FASTMCP_HOST`/`FASTMCP_PORT`, which the `mcp` SDK does not read**, and the SDK's own default is `127.0.0.1:8000` — unreachable behind the Edge proxy.
- **There is no local Edge emulator.** The only honest end-to-end test of an Edge deployment is deploying and probing it.

## Decision

Run two Wasmer apps.

**`fps-cv-mcp`** — a Python/WASIX Edge app built by `anybuild`, serving stateless streamable HTTP at `/mcp`. Code changes required and adopted: bind `0.0.0.0` explicitly (never loopback — it is unreachable behind the proxy and trips the SDK's DNS-rebinding allowlist), resolve the port from `("PORT", "FASTMCP_PORT")` with a literal fallback, and expose both shapes `anybuild` can start from — a repo-root `main.py` with a module-level `app` and a `__main__` guard, plus a `sys.path` insertion of the app root because the start command's working directory is not contractually documented. `runtime.txt` is deleted (a render.com convention; `anybuild` reads the Python version from `pyproject.toml`).

**`fps-cv`** — a Wasmer static site (`wasmer/static-web-server` + `public/`), whose content is generated by the publish workflow rather than committed. The run fails if a subsequent `GET /` does not return 200 with the release tag present, so a green publish means the page is genuinely live.

**Deployment always stages.** `scripts/deploy.sh` copies `git ls-files` output into a temp directory, materialises the fallback data snapshot into it, asserts `wasmer --version >= 7.0`, normalises `WASMER_BIN` to an absolute path (anybuild runs from the staging directory, so a relative binary path resolves there and fails with a bare "No such file or directory"), and only then invokes `anybuild`. `anybuild` is never run from the repository root.

**`/healthz` is the verification surface**, returning 200 only when a validated snapshot is loaded and carrying `origin`, `release_tag`, `loaded_at`, `refresh_state` and `consecutive_failures` — never an unconditional 200. Because there is no pre-deploy gate, the plan's verification step is a live poke: `/healthz`, then `POST /mcp` `tools/list`, then a content tool call.

**render.com stays live through the entire cutover** and is decommissioned only after the Wasmer endpoint has served real traffic for at least a week. The plugin's MCP URL is repointed only after the live poke passes. Rollback before that point is a one-line revert of a URL.

## Considered Options

### A. Wasmer Edge for both the MCP server and the static site (chosen)

- **Pro**: one platform and one account for both artifacts; the post-2026-07-28 stateless protocol is a natural fit for ephemeral horizontal instances; a thoroughly documented first-party reference implementation exists to copy; static-site hosting is a first-class, documented path rather than an improvisation; scale-to-zero economics suit a CV server's traffic profile.
- **Con**: `anybuild`/WASIX tooling has genuine documented rough edges; a hard `pydantic<2.13.5` ceiling that is already binding and could bite again on a future bump; no pre-deploy test environment; custom-domain and pricing-tier specifics were not confirmed in research.

### B. Stay on render.com for the MCP server; host the HTML elsewhere (GitHub Pages, Netlify, Cloudflare Pages)

- **Pro**: zero migration risk for the component that currently works; no WASIX wheel constraints ever; static hosting on GitHub Pages is free, trivial, and needs no token beyond `GITHUB_TOKEN`; the deployment story becomes *simpler*, not more novel.
- **Con**: two platforms instead of one; the render.com free tier's cold starts are a known annoyance for an MCP server that a client may hit once and abandon; the maintainer gains no leverage from the Wasmer experience already accumulated.

### C. Containers (OCI/Docker) on Wasmer

- **Pro**: would sidestep every WASIX wheel constraint.
- **Con**: no evidence was found that Wasmer Edge accepts arbitrary OCI images — every documented path is WASIX-native. Not currently available.

### D. Fly.io

- **Pro**: container-based, mature, no wheel constraints, static assets servable from the same app.
- **Con**: an entirely new vendor relationship with no prior art in this maintainer's toolchain, evaluated by nobody in the research. Strictly more unknown than either A or B.

## Consequences

**Positive**
- The rendered HTML CV gets a real, public URL for the first time.
- One platform, one token, one CLI for both deployables.
- Statelessness means no session affinity, no sticky routing, no in-memory session to lose on instance churn.
- The staged-deploy discipline means the deployed image contains exactly the tracked files plus a deliberately materialised snapshot — a property the previous buildpack deploy never had.

**Negative**
- Every dependency change now carries a WASIX-availability question. Mitigated by a CI step that queries the WASIX index for the `pydantic-core` ceiling, turning a future silent build break into a scheduled signal.
- No pre-deploy validation exists. Mitigated structurally, not technically: the old deployment stays live, cutover is a URL change, and verification is an explicit live-poke step.
- `anybuild`'s rough edges are absorbed into `scripts/deploy.sh`, which becomes a piece of infrastructure that must itself be maintained.

**Neutral**
- `pixi` platforms widen to include `linux-64` for CI, independent of the deploy target.

## Disconfirmation

**Activation**: yes — the lens sweep fired on Operations (no emulator → keep the old deployment alive and make the live poke a plan step, rather than pretending a gate exists) and on Testability (which is what produced `/healthz` as a designed verification surface rather than an afterthought). Security surfaced nothing: no credentials are in the request path, since all fetched assets are public.

Tier-B cross-model challenge **not invoked**: although the stakes touch "user-visible breaking," the reversal is cheap and explicitly staged (render.com stays live; cutover is a one-line URL change), so this is not a one-way door.

**Falsifier.** This decision is wrong if the Wasmer deployment cannot be made to serve a correct `tools/list` within a bounded number of deploy attempts — say five — or if, once live, it is observed returning bare HTTP 500s with no diagnosable cause (the documented WASIX native-extension trap signature). Either outcome means the platform's failure modes exceed what this project can afford to debug without an emulator.

A second falsifier, on the dependency ceiling: if a *security* update to `pydantic` lands above `2.13.5` before the WASIX index catches up, the project would be forced to choose between a known vulnerability and its deployment platform. One occurrence of that bind falsifies the claim that the ceiling is a manageable inconvenience.

**Steelmanned runner-up.** Option B — keep render.com, publish the HTML to GitHub Pages — is genuinely strong and arguably the Simplicity-First answer. It requires *zero* code changes to the server (no bind-host fix, no port-env tuple, no `main.py` shim), zero dependency ceilings, zero build-tool sharp edges, and no staged-deploy script; GitHub Pages needs no new token at all, since `GITHUB_TOKEN` already suffices, which would make the publish workflow simpler than the Wasmer path. The entire case for Wasmer rests on platform consolidation and on leverage from experience the maintainer already has — real benefits, but strategic ones, not correctness ones. If the WASIX constraints prove more expensive than estimated, option B is not a fallback but the better original answer.

**Reversal trigger.** Revert to render.com (and move the static site to GitHub Pages) if either falsifier fires, or if the Wasmer MCP endpoint's availability over the first month is measurably worse than render.com's was. The reversal is deliberately cheap and explicitly sequenced: render.com is not decommissioned until the new endpoint has a week of real traffic, and the plugin's URL is a single JSON field.
